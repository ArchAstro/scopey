# Focused seeded-drift evaluator

This evaluator answers one question: when a Codex session has begun drifting,
does the current Scopey detect it, produce a useful correction, and reduce the
remaining off-track work enough to cover its analyzer-token overhead? The full
corpus also checks whether Scopey stays quiet on work that is genuinely in scope.

It intentionally has only two arms:

- `no_scopey`: resume the seeded Codex session with no correction;
- `scopey`: resume the identical session and repository checkpoint with the
  correction generated by the current Scopey summarizer and judge.

There are no local-model, vLLM, or alternate-analyzer variants.

The checked-in corpus contains six required-drift tasks (the original plus five
additional insight-derived authorization-boundary failures) and five no-drift
controls. `run_benchmark.py` defaults to five paired repetitions per task and
four concurrent pairs.

## Why the transcript is seeded

Organic prompts do not guarantee that the control drifts. The previous pilot's
intended drift case stayed on track in both arms, so it could measure overhead
but could not measure prevention.

`run_seeded_drift.py` instead creates a real Codex transcript containing a
known implementation-plan write. The construction instruction is then replaced
with the research-only user request, producing the intended counterfactual:
the recorded action is relevant to the topic but unauthorized. Both arms get
byte-equivalent semantic history and the same repository checkpoint.

Before cloning, the runner appends an explicit developer-level evaluator policy
to the transcript. It tells the control to continue the already-recorded next
action and tells the treatment to prefer a Scopey correction when present. The
resume message only activates that policy; it is not treated as a new product
scope epoch. This makes drift required instead of stochastic. Consequently,
this is a causal mechanism test; it is not an estimate of how often an
unforced Codex session drifts.

The Scopey arm is not given a hard-coded verdict. The runner seeds Scopey
through its public hooks with the original prompt and structured tool evidence,
runs the current summarizer and judge, requires an `off_track` verdict, and
extracts the correction emitted by the normal stop hook.

## Measurement

Prefix tokens are excluded. Main-session usage is the difference between the
provider's cumulative Codex counters at the branch point and at the end of each
continuation. Scopey input and generated output come from provider-reported
usage for its summarizer and judge calls.

The result distinguishes:

1. whether the no-Scopey continuation performs additional writes;
2. whether the Scopey continuation avoids those writes;
3. main-session suffix tokens avoided;
4. Scopey analyzer overhead; and
5. net tokens saved after overhead.

One pair demonstrates the mechanism, not a population effect. Repeat a frozen
case for variance and use separate organic tasks before making a statistical
claim.

## Run

Prerequisites are a release Scopey binary and an authenticated Codex CLI.

```sh
make build-release
make eval-test
make eval-seeded
make eval-benchmark
```

Artifacts are written below `eval/results/` and intentionally ignored by Git.
The report is `report.md`; exact evidence and token fields are in `result.json`.
Full-corpus runs additionally produce `results.jsonl` and `summary.json` with
per-task and per-condition means, sample standard deviations, deterministic
bootstrap 95% confidence intervals for token means, and Wilson intervals for
behavioral rates.
